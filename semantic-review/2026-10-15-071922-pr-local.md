# Input handling robustness in Brick Buster

The game funnels all keyboard input through one `keydown` listener on `document` that dispatches by game state, plus an unconditional `keyup` that clears paddle-movement flags and a `mousemove` on the canvas that drives the paddle directly. ENTRY routes to a pure reducer wiring (`handleEntryKey`/`applyEntryKey`), and READY consults a reset controller (`handleReadyKey`) before the Space-to-start branch. Key matching is thorough: both `e.key` and legacy aliases (`Left`/`Right`), both cases of `p`/`P`/`y`/`Y`/`n`/`N`, and a case-insensitive letter regex in the entry reducer, all guarded against missing/odd `e.key` so nothing throws on an exotic key. The dispatch order is sound — ENTRY and a handled READY reset both `return`/short-circuit before Space-to-start, so inputs aren't double-handled across those paths.

The gaps are around physical key state surviving focus changes and around inputs that reach the paddle outside of play. Watch for: paddle arrows never call `preventDefault`, so arrow keys scroll a scrollable page during play (confirmed); there is no `blur`/`visibilitychange` reset, so a held arrow lost to alt-tab leaves `keys.left`/`keys.right` stuck (confirmed); and `mousemove` moves the paddle in every state including PAUSED and ENTRY (confirmed).

**Verdict**: NEEDS_CHANGES

## Stuck paddle flags on focus loss

`keys.left`/`keys.right` are set only inside the `state === STATE.PLAYING` branch of `keydown`, and `keyup` clears them unconditionally — so a flag left set across PLAYING→ENTRY is harmless (`update()` early-returns outside PLAYING) and clears on the eventual `keyup`. The hole is the `keyup` that never arrives. If the player holds Left and alt-tabs (or the window otherwise loses focus), the browser delivers no `keyup`, so `keys.left` stays `true`. On return to a PLAYING field the paddle slides left with no key held until the player taps and releases that arrow. There is no `window.blur` or `document.visibilitychange` handler to zero the flags, which is the standard fix:

```js
window.addEventListener("blur", function () { keys.left = false; keys.right = false; });
```

## Arrows scroll the page

In the PLAYING branch the arrow keys set movement flags but never call `preventDefault`:

```js
if (state === STATE.PLAYING) {
  if (e.key === "ArrowLeft" || e.key === "Left") keys.left = true;
  if (e.key === "ArrowRight" || e.key === "Right") keys.right = true;
}
```

Space and P are prevented, and the ENTRY handler prevents arrows, but gameplay arrows are not. On any page tall enough to scroll (the layout is `min-height: 100vh`, so a short viewport scrolls), holding an arrow to move the paddle also scrolls the window, dragging the canvas out of view mid-game. Calling `e.preventDefault()` on the arrow keys inside this branch closes it without affecting the ENTRY path, which already prevents them separately.

## Mouse control is not state-gated

`mousemove` recomputes and clamps `paddle.x` on every move regardless of state, and only the ball-follow is gated to READY:

```js
canvas.addEventListener("mousemove", function (e) {
  ...
  paddle.x = mouseX - paddle.w / 2;
  paddle.x = Math.max(0, Math.min(W - paddle.w, paddle.x));
  if (state === STATE.READY) ball.x = paddle.x + paddle.w / 2;
});
```

Moving the mouse while PAUSED slides the paddle behind the overlay, so pausing to stop and reposition the mouse teleports the paddle on resume — pause doesn't actually freeze paddle position. The same write fires during ENTRY and the OVER/WIN screens; it's cosmetic there (the paddle is hidden behind a full-screen overlay) but it means the clamp math runs on input that should be inert. Gating the paddle write to `READY`/`PLAYING` makes pause behave as expected and keeps the terminal/entry states free of stray paddle motion.

## Key repeat re-triggers restart

The start/restart branch has no `e.repeat` guard:

```js
if (e.code === "Space" || e.key === " ") {
  e.preventDefault();
  initAudio();
  if (state === STATE.READY || state === STATE.OVER || state === STATE.WIN) startPlaying();
}
```

Holding Space on the GAME OVER / WIN screen fires `keydown` repeatedly; each repeat that still sees a terminal state calls `startPlaying()` → `newGame()` again. In practice the first call flips state to PLAYING and later repeats fall through harmlessly, so the visible effect is small, but a held key doing repeated full resets is fragile. Ignoring auto-repeat (`if (e.repeat) return;` at the top, or on this branch) makes start/restart a clean single-shot.

## Enter is not an alias for Space

Start, restart, and initials-confirm are all Space-only. `handleReadyKey` explicitly treats everything except Y/N as inert while a reset is pending, and the confirm key in `applyEntryKey` matches only `" "`/`"Space"`. Players habitually press Enter to confirm initials and to dismiss end screens; neither does anything here. If Enter-to-confirm/start is desired, add `"Enter"` alongside the Space checks in the start branch and the reducer's confirm branch. Flagged as a usability gap, not a correctness bug.
