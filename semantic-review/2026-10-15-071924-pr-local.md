# Game loop runs full-cost rendering every frame in all states, with fixed per-frame physics

The game loop in `index.html` is a classic `update()` → `render()` → `requestAnimationFrame` cycle. It is correct and the game is small (50 bricks, ~10-50 particles), so on a 60 Hz display it will not drop frames on any modern machine. The performance issues are structural rather than fatal: physics advances by fixed per-frame deltas (no elapsed-time integration), so the game runs at whatever rate the display refreshes — twice as fast on a 120 Hz monitor. Rendering does a full-canvas clear plus a full redraw of every static element, plus a per-pixel-row scanline pass and heavy per-glyph shadow/glow work, on *every* frame regardless of state — so an idle READY, PAUSED, OVER, or WIN screen that never changes still burns a full render budget forever. Per-frame object/string allocations in the HUD and leaderboard draw paths add steady GC pressure.

Watch for: frame-rate-dependent physics (confirmed) — the game is unplayable-fast on high-refresh displays. Full render + scanline + glow work in static states (confirmed) — wasted battery/CPU on screens that never change. Per-glyph `shadowBlur` is the single most expensive draw cost (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

Physics in `update()` adds raw velocity to position once per frame (`ball.x += ball.dx`, `paddle.x -= paddle.speed`) with no timestep. The loop is driven by `requestAnimationFrame`, whose cadence follows the display, so every speed in the game is implicitly "per refresh" rather than "per second." On a 120/144 Hz panel the ball and paddle move 2–2.4× faster. This is the highest-severity finding because it changes gameplay, not just cost.

`render()` unconditionally clears the whole canvas and repaints bricks, paddle, ball, HUD, and a full scanline overlay every frame, then layers state-specific overlays. Four of the six states (READY, PAUSED, OVER, WIN) are visually static apart from one blinking prompt, yet they pay the same cost as active play. The loop could skip rendering entirely when nothing has changed, or at least skip the gameplay-field redraw behind an opaque-enough overlay.

The dominant per-pixel cost is `drawScanlines()`, which issues ~200 `fillRect` calls every frame to paint 1px lines across an 800×600 canvas, and `glowText()`, which sets `shadowBlur` for every text draw — shadowed canvas fills are among the most expensive 2D operations. Both produce an identical result every frame and are prime candidates for caching to an offscreen canvas.

Allocation churn is minor but avoidable: `drawHUD`, `drawLeaderboard`, and the READY branch build fresh strings and arrays of option objects every frame.

1. **Frame-rate-dependent physics (High)** — `update()` integrates with fixed per-frame deltas; game speed scales with refresh rate. Switch to elapsed-time integration using the `requestAnimationFrame` timestamp (fixed-step accumulator or `dt` multiplier).
2. **Full render every frame in static states (High)** — READY/PAUSED/OVER/WIN redraw the whole scene forever though nothing changes. Gate `render()` on a dirty flag or state change so static screens draw once.

5. **Per-frame string/array/object allocation in draw paths (Low)** — `drawHUD`, `drawLeaderboard`, and the READY `lines` array allocate fresh strings/objects every frame. Cache formatted strings and hoist constant option arrays.

### Frame-rate-dependent physics

`update()` advances everything by a raw per-call delta: `ball.x += ball.dx`, `ball.y += ball.dy`, and `paddle.x -= paddle.speed` / `+= paddle.speed`. There is no elapsed-time term anywhere in the loop — `loop()` ignores the timestamp `requestAnimationFrame` passes to its callback. Because rAF fires once per display refresh, every one of those deltas is really "per refresh," not "per second." On a 60 Hz monitor `BALL_BASE_SPEED = 5.5` means 330 px/s; on a 144 Hz monitor the same constant means 792 px/s and the paddle moves 8 px × 144 = 1152 px/s. The game is simply faster on faster displays, and slower if the tab is throttled.

The fix is to integrate against elapsed time. Capture the timestamp rAF already provides, compute `dt` since the last frame, and either multiply every delta by `dt` normalized to a target rate, or run a fixed-step accumulator (advance `update()` in fixed 1/60 s increments, consuming accumulated real time). A fixed-step accumulator is the better fit here because the collision code assumes small, uniform steps — note the "one brick per frame" early `return` in the brick loop, which already couples physics resolution to frame count. Variable `dt` scaling would need that collision logic revisited; a fixed-step loop preserves it unchanged.

### Full render every frame regardless of state

`loop()` calls `render()` unconditionally, and `render()` always runs `ctx.clearRect(0,0,W,H)`, `drawBricks()`, `drawParticles()`, `drawPaddle()`, `drawBall()`, `drawHUD()`, the per-state overlay, and `drawScanlines()`. In READY, PAUSED, OVER, and WIN the underlying scene never changes — the ball and bricks are static, and `update()` early-returns in every non-PLAYING state. The only moving pixels are the READY "insert coin" blink (toggles twice a second via `Math.floor(Date.now()/500)%2`) and any in-flight particles. So four states repaint an identical frame 60+ times a second indefinitely. On a laptop this keeps the GPU/CPU awake and drains battery on a screen that looks frozen.

A dirty-flag approach fixes this: render once on entering a static state, and re-render only when something changes (state transition, status message, or the READY blink tick). The blink can be driven by its own low-frequency check so the main loop can otherwise idle. PAUSED, OVER, and WIN have no animation at all and can render exactly once.

```
loop(ts):
  update()                       // physics only when PLAYING
  if PLAYING: updateParticles()
  if PLAYING or dirty or particles.length: render()
  requestAnimationFrame(loop)
```

### glowText shadow cost dominates text rendering

```js
function glowText(text, x, y, color, font, blur) {
  ctx.save();
  ctx.fillStyle = color;
  ctx.font = font;
  ctx.shadowColor = color;
  ctx.shadowBlur = blur != null ? blur : 12;
  ctx.fillText(text, x, y);
  ctx.restore();
}
```

Every piece of text in the game goes through this, and a non-zero `shadowBlur` forces the canvas to render the glyph into a temporary buffer and run a blur kernel — one of the most expensive operations in the 2D API. During PLAYING, `drawHUD()` alone calls `glowText` five-plus times per frame (LIVES, BRICKS count, SCORE label, score value, and COMBO when active); the leaderboard screens call it up to ten more times. Setting `ctx.font` repeatedly also triggers font re-parsing.

The HUD glow is constant per visual state except for the score/combo digits, so the static labels ("LIVES", "SCORE", the hearts, the leaderboard rows) can be pre-rendered once to an offscreen canvas and blitted. For the live score and combo, either accept a plain fill (no shadow) or render the glow version only when the value changes and cache the resulting bitmap. Even just hoisting the glow work off the per-frame path for the static strings removes most of the cost.

### Scanlines repaint a constant pattern every frame

```js
function drawScanlines() {
  ctx.save();
  ctx.fillStyle = "rgba(0,0,0," + THEME.scanlineAlpha + ")";
  for (let y = 0; y < H; y += THEME.scanlineGap) {
    ctx.fillRect(0, y, W, 1);
  }
  ctx.restore();
}
```

With `H = 600` and `scanlineGap = 3` this issues 200 `fillRect` calls every frame, and the result is byte-for-byte identical on every frame since nothing about it depends on game state. It also builds the `rgba(...)` string once per call via concatenation. This is pure repeated work. Render the scanline grid once into an offscreen canvas (or a 1×`gap` `createPattern` tile) at startup and draw it with a single `drawImage`/pattern fill each frame — or fold it into the dirty-flag scheme so it only redraws when the frame beneath it does.

### Per-frame allocations in the draw paths

`drawHUD` builds `"BRICKS " + (totalBricks - destroyed)`, `String(score).padStart(6,"0")`, and `"COMBO X" + combo` every frame; `drawLeaderboard` builds a rank/initials/score string per row every frame; and the READY branch allocates a fresh `lines` array of option objects on every render. None of these is large, but together they produce steady short-lived garbage that the GC must sweep. The leaderboard and READY strings only change on state transitions, so they can be formatted once and cached. The score/combo strings change at most once per brick hit, so they can be rebuilt only when `score`/`combo` change rather than every frame. The READY `lines` array (apart from the toggling prompt entry) is constant and can be hoisted to module scope.

### Particle update/draw asymmetry

`drawParticles()` runs in every state (it is called unconditionally at the top of `render()`), but `loop()` only calls `updateParticles()` when `state === STATE.PLAYING`. If a brick is destroyed on the final hit that triggers `endRound("win")` — or the ball-drop that triggers `endRound("over")` — the spawned particles are drawn but never advanced once the state flips, so a cluster of particles freezes mid-flight on the end screen until the next game clears them. This is a polish/correctness artifact rather than a cost issue. If the frozen cluster is not intended, gate the update on `particles.length > 0` instead of on the state.
